# DU-HACKSGIVING Specification and Code Review

Review target: repository `main` at commit `df16b60c1afa92e75e3d40d0aceb19c4dc61bd0b`.

Scope: read-only review of the implementation against `SPEC.md`, plus bugs, error handling, code quality, and platform best practices. No application code was changed.

## Findings

1. **[WARN] The project is not React Native or Expo.** The repository contains a native iOS app built with SwiftUI, SwiftData, Vision/VisionKit, AlarmKit, and UserNotifications. There is no `package.json`, Expo configuration, JavaScript, TypeScript, JSX, or TSX source. The single application target is declared in `PillBox.xcodeproj/project.pbxproj:94-115`, and the app entry point is `PillBox/PillBoxApp.swift:4-24`. React Native/Expo-specific best practices therefore cannot be evaluated; the rest of this review assesses the actual native implementation.

2. **[WARN] The “mobile devices with smartwatch integration” criterion is only partially met.** The project has one iPhone-only target (`TARGETED_DEVICE_FAMILY = 1`) and requires iOS 26 (`PillBox.xcodeproj/project.pbxproj:157,184,222,254`). AlarmKit alarms may appear on a paired Apple Watch, but there is no watchOS target, Watch app, Watch complication, or independent watch interaction. There is also no Android implementation. This is an iPhone app with system-level watch alarm presentation, not a cross-platform mobile app with a smartwatch companion.

3. **[PASS] Users can scan a medication label with the live camera.** `TakeScanView` starts a VisionKit `DataScannerViewController` and streams recognized text into `ScanSession` (`PillBox/Views/AddMedFlow.swift:89,128-157,288-303,383-404`). Camera authorization is requested before live scanning (`AddMedFlow.swift:293-302`).

4. **[PASS] Users can select multiple label photos from the photo library.** The photo picker accepts up to ten ordered images and combines their OCR results into one scan session (`PillBox/Views/AddMedFlow.swift:107-121,305-335`). `LabelReader` performs on-device Vision text recognition (`PillBox/Logic/LabelReader.swift:4-26`). This correctly supports photographing multiple sides of one curved bottle.

5. **[WARN] Photo import and OCR failures are silently discarded.** Photo loading uses `try?` and skips failed items without telling the user (`PillBox/Views/AddMedFlow.swift:112-121`). OCR also uses `try?`; a recognition error simply ends or produces an incomplete scan (`AddMedFlow.swift:314-335`). `DataScannerViewController.startScanning()` errors are ignored (`AddMedFlow.swift:401-404`). The UI needs an explicit error state with retry and manual-entry options so camera, photo-decoding, and OCR failures are distinguishable from “no text found.”

6. **[PASS] The parser attempts to identify medication name, strength/dosage, dose amount, frequency, expiration, prescriber, quantity, refills, and other label fields.** The parsed data model is defined in `PillBox/Logic/LabelParser.swift:5-35`; parsing is performed in `LabelParser.parse` (`LabelParser.swift:38-104`). `ScanSession` uses repeated-frame voting before accepting important values (`PillBox/Logic/ScanSession.swift:20-41,92-123,128-163`), which is a sensible design for noisy OCR.

7. **[FAIL] Weekly prescriptions can be scheduled on the wrong day without the user seeing it.** When text says “weekly” but does not include a weekday, the parser silently substitutes the weekday on which the bottle was scanned (`PillBox/Logic/LabelParser.swift:192-197`). The redesigned confirmation screen shows only a general “Time” row (`PillBox/Views/AddMedFlow.swift:438-466`), and its time editor has no weekday control (`AddMedFlow.swift:527-641`). The app should mark the weekday as missing and require the user to choose it; inventing a schedule is unsafe.

8. **[WARN] Date parsing accepts invalid calendar dates by normalization.** `makeDate` checks only that the month is 1...12 and the day is at most 31 (`PillBox/Logic/LabelParser.swift:527-540`). Foundation can normalize values such as February 31 into a date in March, so a bad OCR result can become a believable but incorrect expiration date. The constructed date should be round-tripped through calendar components and rejected unless year, month, and day exactly match the input.

9. **[PASS] The app supports an arbitrary number of medications and persists them.** Medications are SwiftData models, and the add flow inserts new records without a fixed application limit (`PillBox/Models/Models.swift:16-53`; `PillBox/Views/AddMedFlow.swift:717-772`). The pill-box grid grows with `meds.count` (`PillBox/Views/MediPillBox.swift:6-34`). Practical limits are device storage and notification capacity rather than an application-side medication limit.

10. **[PASS] The app provides a virtual pill box and daily calendar/schedule.** `MediPillBoxView` displays one compartment per medication (`PillBox/Views/MediPillBox.swift:4-63`). `TodayView` builds the selected day’s dose slots and lists every medication at each time (`PillBox/Views/TodayView.swift:19-38,46-76`). `Scheduler.slots` groups medications by day and time (`PillBox/Logic/Schedule.swift:123-137`).

11. **[PASS] Morning, afternoon, evening, and night schedules are implemented, and exact times can be entered.** The model stores day parts and custom minute-of-day values (`PillBox/Models/Models.swift:30-36`). The redesigned editor supports part-of-day and exact-time modes (`PillBox/Views/AddMedFlow.swift:529-565,579-641`), and `Scheduler.times` resolves them (`PillBox/Logic/Schedule.swift:108-121`).

12. **[FAIL] Reminder coverage ends after tomorrow unless the user reopens the app.** `rescheduleNow` creates alarms and notifications only for offsets `0...1`, meaning today and tomorrow (`PillBox/Services/ReminderService.swift:98-119`). Rescheduling occurs when the root view launches, becomes active, or observes a medication-count change (`PillBox/Views/RootView.swift:53-80`); no background refresh task maintains the rolling horizon. If the app is not opened for more than two days, later doses have no scheduled alarm or backup notification, violating the core reminder criterion.

13. **[WARN] The Lock Screen alarm is implemented, but the code cannot guarantee an undismissable notification.** AlarmKit fixed alarms are scheduled with Taken and Open actions (`PillBox/Services/ReminderService.swift:136-180,322-358`). The app persists an awaiting-confirmation slot and restores the full-screen confirmation screen (`PillBox/Services/AppModel.swift:44-60`; `PillBox/Views/RootView.swift:91-105`). However, iOS still controls the system alarm UI, and a user can stop/dismiss system presentation without immediately confirming. The app compensates with an awaiting state and follow-up notifications, but it cannot literally make an iOS notification “not go away.” The spec/UX copy should describe the achievable behavior precisely.

14. **[FAIL] Backup notification delivery can exceed the platform budget and fail silently.** Every dose slot schedules eight follow-ups, or nine notifications when AlarmKit is unavailable (`PillBox/Services/ReminderService.swift:211-231`). Four distinct dose times over today and tomorrow already consume 64 requests before expiration warnings are added. Only expiration requests are capped, independently, at sixteen (`ReminderService.swift:242-266`). `UNUserNotificationCenter.add` results are not awaited or checked, so capacity or authorization failures are invisible. The service needs one global soonest-first notification budget and explicit scheduling-error handling.

15. **[FAIL] Backup notifications use a critical sound without requesting or configuring critical-alert permission.** Permission requests include only `.alert`, `.sound`, and `.badge` (`PillBox/Services/ReminderService.swift:46-50`), while backup notifications use `.defaultCritical` (`ReminderService.swift:219-224`). The Xcode project has no critical-alert entitlement. These notifications therefore cannot reliably provide the intended critical sound through Silent or Focus. AlarmKit may still handle the initial alarm, but the backup guarantee is not correctly implemented.

16. **[PASS] The in-app confirmation screen lists all medications due for the slot and provides a confirmation button.** `TakeMedsView` iterates over `slot.meds`, shows each medication and dose, and provides one “I took it/all” action (`PillBox/Views/TakeMedsView.swift:35-67,94-97`). Confirmation creates a `DoseLog`, decrements the relevant bottles, clears snooze state, and cancels remaining reminders (`PillBox/Services/AppModel.swift:65-89`).

17. **[WARN] Confirmation persistence errors are ignored.** `DoseActions.markTaken` uses `try?` for fetching and saving (`PillBox/Services/AppModel.swift:66-87`). If the database fetch fails, it assumes there is no existing log; if saving fails, it still cancels reminders and closes the confirmation screen. A user could believe a dose was recorded while no durable log exists. Saving must succeed before reminders are canceled, with an error state and retry path if it does not.

18. **[PASS] Expiration dates are tracked per physical bottle, including multiple bottles of one medication.** `Medication` owns multiple `Bottle` records; every bottle has its own expiration, quantity, Rx number, label text, and image (`PillBox/Models/Models.swift:16-18,47-48,79-98`). `MedSaver` merges the same normalized medication name and strength while inserting a new bottle (`PillBox/Views/AddMedFlow.swift:717-750`). This correctly preserves separate expirations for duplicate medication bottles.

19. **[PASS] Expiration warnings are scheduled at one month, two weeks, one week, and the day of expiration.** `scheduleExpiryWarnings` iterates `[30, 14, 7, 0]` for every active bottle (`PillBox/Services/ReminderService.swift:242-266`). `ExpiryLevel` also classifies month, two-week, one-week, today, and expired states for in-app display (`PillBox/Logic/Expiry.swift:3-36`).

20. **[PASS] Expired medication is visibly identified and the user is urged to scan a replacement bottle.** `AlertsView` separates expired bottles, labels them “Expired — don't take these,” and provides “Scan new bottle” (`PillBox/Views/AlertsView.swift:18-37,80-108`). The expiration-day notification also asks the user to scan a new bottle (`PillBox/Services/ReminderService.swift:251-259`).

21. **[FAIL] The original bottle-label image is not reliably retained.** Live camera recognition streams text but never captures a still image; `finish()` passes `stillImage`, which remains `nil` in live mode (`PillBox/Views/AddMedFlow.swift:128-157,338-342`). Imported multi-photo scans retain only the currently displayed image, not all uploaded sides (`AddMedFlow.swift:308-320,338-342`). `MedSaver` then stores only that single optional image (`AddMedFlow.swift:739-750`). Consequently, bottles scanned live have no original label photo, and multi-image evidence is discarded. This fails the spec’s original-label requirement.

22. **[WARN] Prescriber contact and refill-message composition are present, but practitioner notification is not automated and preference toggles are ineffective.** The app can associate a `Prescriber`, generate an expiration/low-supply refill request, and open text or email composition (`PillBox/Models/Models.swift:100-114`; `PillBox/Views/PrescriberViews.swift:34-125`). It intentionally leaves the recipient blank and requires the user to send. More importantly, `notifyWhenExpiring` and `notifyWhenLow` are exposed as toggles (`PrescriberViews.swift:14-21`) but are never consulted by `AlertsView` or reminder scheduling. Message offers appear regardless of the selected preferences (`PillBox/Views/AlertsView.swift:48-67,80-108`).

23. **[FAIL] The app cannot cover activity in another foreground app as the literal spec requests.** When MEDI itself is foregrounded, the notification delegate opens `TakeMedsView` and suppresses the banner (`PillBox/Services/ReminderService.swift:293-303`), and AlarmKit updates also trigger the in-app cover (`ReminderService.swift:183-202`). If the user is in another app, iOS controls the alarm presentation; this application cannot draw a custom full-screen view over that app. The implementation covers MEDI and uses system AlarmKit elsewhere, so the requirement must be revised to match iOS platform constraints.

24. **[FAIL] Snoozing can cross into a different day period when a dose is already overdue.** Normally `SnoozeStore.options` caps snooze at the current dose’s day-part end. But if that period has already ended, it allows `base + 15 minutes` up to end of day (`PillBox/Logic/Schedule.swift:186-195`). For example, opening a morning dose after noon permits an afternoon snooze, contradicting the explicit same-period requirement. The overdue case needs a different policy that does not silently cross the boundary.

25. **[PASS] The confirmation screen itself cannot be interactively dismissed.** `TakeMedsView` uses `.interactiveDismissDisabled()` and offers only confirm or snooze actions (`PillBox/Views/TakeMedsView.swift:59-88`). `AppRouter` also saves the awaiting slot in `UserDefaults` so it can return on the next launch (`PillBox/Services/AppModel.swift:44-60`).

26. **[FAIL] Minimum-hours-apart enforcement can silently remove required doses.** `Scheduler.enforceGap` pushes conflicting times later, but if a pushed time is past 23:59 it simply omits it (`PillBox/Logic/Schedule.swift:93-106`). The UI and model can still say multiple daily doses are required while fewer reminders are returned. For example, four selected day parts with an eight-hour minimum can collapse to two actual times. The app must preserve the prescribed dose count, show an unsatisfiable-schedule error, or require the user to resolve the conflict.

27. **[PASS] “Every N hours” directions are recognized and translated into reminder times.** `LabelParser.parseFrequency` detects “every N hours,” stores the interval and minimum gap (`PillBox/Logic/LabelParser.swift:169-185`), and `Scheduler.intervalTimes` spaces doses through waking hours (`PillBox/Logic/Schedule.swift:82-90,108-120`). The implementation exists, subject to the dropped-dose issue in finding 26.

28. **[WARN] Data-layer errors are broadly swallowed.** Besides dose confirmation, medication saving, edits, deletion, demo reset, health-profile encoding, and multiple fetches use `try?` and continue as though successful (`PillBox/Views/AddMedFlow.swift:722-723,770-771,785-795`; `PillBox/Views/MediPillBox.swift:127-132`; `PillBox/Views/InfoView.swift:23-30`; `PillBox/Demo/DemoData.swift:9-17`). For medication data, silent failure is inappropriate. Centralized persistence functions should return results and present actionable errors.

29. **[WARN] A database-open failure crashes the app with no recovery path.** `AppModel.container` calls `fatalError` if SwiftData initialization fails (`PillBox/Services/AppModel.swift:5-15`). Migration incompatibility, corruption, or storage problems therefore prevent the user from opening the app. A production health-related app should provide a recoverable error screen and protect/export existing data before offering reset options.

30. **[WARN] Sensitive health information is stored and shown without an app-level privacy strategy.** Insurance, conditions, allergies, and medication history are JSON in `UserDefaults` (`PillBox/Views/InfoView.swift:4-30`). Notification bodies include medication names on the Lock Screen (`PillBox/Services/ReminderService.swift:211-226`). The project has no visible privacy toggle for redacting notification content, no app lock, and no documented data-protection policy beyond “on device.” At minimum, users should be able to hide medication names in notifications, and sensitive profile data should use an explicitly protected store.

31. **[WARN] Deleting a medication behaves differently depending on the screen used.** Deleting from the pill-box detail records the medication under Past medications and reschedules reminders (`PillBox/Views/MediPillBox.swift:127-132`). Deleting through the Info tab’s `MedicationDetailView` directly deletes and saves without calling `HealthProfile.recordStopped` (`PillBox/Views/MedicationDetailView.swift:94-109`). This contradicts the app’s own Past-medication behavior and indicates duplicated deletion logic.

32. **[WARN] Several production code paths are duplicated or obsolete.** The project includes both `MediPillBoxView` and `PillBoxView`, both `MedDetailCard` and `MedicationDetailView`, and two separate medication-saving implementations in `MedicationFormView.save` and `MedSaver.save` (`PillBox/Views/MediPillBox.swift:6`; `PillBox/Views/PillBoxView.swift:5`; `PillBox/Views/MedicationDetailView.swift:4`; `PillBox/Views/MedicationFormView.swift:361-401`; `PillBox/Views/AddMedFlow.swift:717-795`). The differing deletion behavior demonstrates the maintenance risk. Shared domain actions should be extracted, and unused legacy screens should be removed after confirming navigation coverage.

33. **[WARN] Reminder-service naming and product naming are inconsistent.** The code, bundle display name, logger subsystem, permission copy, and filenames use “PillBox,” while many screens use “MEDI” (`PillBox.xcodeproj/project.pbxproj:205,218`; `PillBox/Services/ReminderService.swift:35`; `PillBox/Views/AddMedFlow.swift:69,302`). This is confusing in permission prompts, Settings, logs, screenshots, and support documentation. Select one product name and apply it consistently.

34. **[WARN] No automated test target or test files exist.** The Xcode project declares only the `PillBox` application target (`PillBox.xcodeproj/project.pbxproj:94-115`), and there are no unit/UI test sources. `LabelParser`, `Scheduler`, snooze boundaries, DST/time-zone changes, expiration thresholds, duplicate-bottle merging, notification budgeting, and persistence failure behavior are high-risk logic that should have deterministic tests.

35. **[PASS] The current Swift implementation compiles and passes Xcode static analysis.** An unsigned generic-iOS Debug build completed successfully with `xcodebuild`, and the Xcode `analyze` action completed without diagnostics. This confirms the reviewed commit is syntactically buildable; it does not validate the runtime notification guarantees or replace missing tests.

## Overall assessment

The repository is a polished native iOS hackathon prototype with thoughtful OCR voting, separate bottle records, strong visual design, and a real AlarmKit-based reminder flow. It implements most visible screens and much of the functional concept. The principal release blockers are the two-day reminder horizon, notification-capacity and critical-alert handling, missing retention of live-scanned label images, unsafe weekly-day inference, cross-period overdue snoozing, and silent persistence failures. These should be resolved and covered by tests before the app is relied on for medication adherence.
